# 对话附件展示收敛设计

## 背景

当前用户消息会在附件下面额外展示一张“附件已处理 / 已作为原生图片输入”卡片。该卡片暴露的是内部路由过程，而且现有实现会把 OCR 路由错误显示成原生图片输入。用户不关心传输路线，只关心附件本身和真实发生的识别过程。

同时，当前用户消息先展示文字、再展示附件。对于“解析一下 + 图片”这类输入，先看到附件再看到用户说明更符合阅读顺序。

## 目标

1. 用户消息中不再渲染任何 `transformation` 附件转换卡片。
2. 用户消息中的附件排在文字上方。
3. 不修改持久化消息和 part 的顺序，只调整 Desktop 的展示模型，避免影响导出、重放、编辑和协议兼容。
4. OCR 的真实工具过程继续显示在 Assistant 区域；附件路由失败继续通过现有运行失败提示表达。

## 展示规则

### 用户消息

按以下顺序展示：

1. `attachment` parts，保持用户添加附件时的相对顺序；
2. `text` parts，保持原有文本顺序；
3. 其他允许出现在用户消息中的可见 parts，保持稳定顺序。

`transformation` parts 一律不进入可见 transcript，因此不再出现：

- “附件已处理”；
- “已作为原生图片输入”；
- “文档内容”；
- “工具资源”。

### Assistant 消息

Assistant 工具过程不受用户消息排序影响。`ImageToText` 实际执行时仍显示：

- 正在识别图片文字；
- 已识别图片文字；
- 图片中未识别到文字；
- 图片文字识别失败。

这类状态来自真实工具执行，不能由附件路由卡片代替。

## 数据流边界

Server 仍保存 `transformation` parts，供诊断、事件重放和未来审计使用。Desktop 在 `visibleTranscriptParts` 阶段过滤这些内部 parts，再在用户消息渲染模型中把附件排到文本之前。

不删除数据库记录，不修改协议 union，不重写历史数据。

## 错误处理

- 路由失败时，不恢复 transformation 卡片；沿用 run error notice 显示具体失败原因。
- OCR 工具失败时，由 Assistant 的 `ImageToText` 工具状态显示失败。
- 图片成功直传模型时，只展示附件本身，不宣称模型已经正确理解图片。

## 测试

1. transcript 可见性测试：`transformation` parts 被过滤，其他 parts 保留。
2. 用户消息渲染测试：输入顺序为文字后附件时，最终 HTML 仍先出现附件名、再出现文字。
3. OCR 工具渲染回归：隐藏 transformation 后，`ImageToText` 的进行中、成功、无文字和失败状态仍可见。
4. Desktop 全量测试与跨包类型检查。

## 验收标准

- 截图红框区域完全消失，不留下空白占位。
- 图片附件展示在用户文字上方。
- 原生图片路径不显示额外状态卡。
- OCR 路径只显示真实的 OCR 工具状态。
- 页面刷新、会话重开和乐观消息替换前后顺序一致。
