# 图片生成占位符与多图展示设计

## 目标

当 `ImageGeneration` 正在执行时，助手消息显示一个专用的图片生成占位符。生成完成后，占位符所在位置显示实际图片；一次返回多张图片时使用有上限的响应式拼图。

本次只修改桌面端的消息展示，不修改生图 Tool、附件协议、消息数据库或服务端投影。

## 现有基础

服务端已经把生成结果导入正式附件系统，并在助手消息中创建带有以下来源信息的附件部件：

```ts
metadata: {
  source: "image_generation",
  toolUseId: string,
}
```

助手消息同时包含 `ImageGeneration` Tool 部件。Tool 的 `pending`、`running`、`completed`、`failed` 和 `interrupted` 状态足以驱动占位符，不需要新增持久状态。

## 内容模型

桌面端的 `buildAssistantContent()` 识别名称为 `ImageGeneration` 的 Tool 部件，并生成专用的图片生成显示单元。该 Tool 不再进入普通的 Tool 活动分组。

显示单元使用 Tool 部件已有的数据：

- `id`：保证同一次生图在重新渲染时保持稳定。
- `status`：决定显示生成中、失败、取消或完成状态。
- `input.ratio`：决定占位区域比例；缺失或无效时使用 `1:1`。
- `createdAt`：在桌面端计算真实等待时间。

生成成功后，现有 `attachment` 显示单元继续负责渲染图片，不把附件合并进新的协议结构，也不复制附件数据。

## 状态与替换行为

### 生成中

当 Tool 状态为 `pending` 或 `running` 时，在 Tool 原本所在的位置显示图片生成占位符，不显示普通的“执行了一个工具”行。

文案按真实等待时间变化：

- 0～10 秒：`正在生成图片`
- 10～45 秒：主标题保持 `正在生成图片`，第二行显示 `已等待 N 秒`
- 超过 45 秒：主标题保持 `正在生成图片`，第二行显示 `已等待 N 秒 · 生成时间可能较长`

等待时间由桌面组件根据 `createdAt` 计算。定时更新只存在于 React 组件内，不写入服务端或数据库。

### 成功

当 Tool 状态为 `completed` 时隐藏专用占位符，后续已经存在的生成附件组自然占据它后面的位置。因为 Tool 部件与附件部件属于同一条助手消息并按顺序持久化，视觉效果是占位符被实际图片替换。

如果消息仍在流式更新、Tool 已完成但附件部件尚未到达，显示轻量行内状态 `正在整理生成结果…`。运行结束后仍然没有生成附件时，不永久显示加载状态，而是显示行内状态 `图片已生成，但附件暂未显示`。

### 失败和取消

- `failed`：同一位置显示紧凑的行内提示，标题为 `这次没有生成出图片`，同一行提供 `详情` 展开入口。外层不再使用整块边框和背景；展开后只在下方使用弱化的内嵌区域显示脱敏后的错误详情。提示图标保留低饱和暖色，不使用大面积红色。
- `interrupted`：同一位置显示 `图片生成已取消`。

除生成中的比例占位面板和成功后的图片画廊外，所有图片生成状态统一使用无外框的行内结构：相同的字号、图标尺寸、水平间距和状态播报方式。取消使用中性图标，整理中使用低调的品牌色图标，失败和附件缺失使用低饱和暖色图标。只有失败且确实存在错误正文时才显示可展开的 `详情`。

本次不增加专用重试按钮。用户仍通过正常对话重新发起生图请求。

## 占位符视觉

占位符使用一个固定为约 `288px` 宽的紧凑圆角容器：

- 顶部显示低调的状态点、稳定标题和第二行等待时间。
- 主体使用低对比度渐变骨架背景。
- 主体固定约 `176px` 高，中央只显示一张小画布轮廓，不暗示未知的生成数量。
- 小画布轮廓跟随 Tool 输入的 `ratio`，支持现有的 `1:1`、`3:4`、`4:3`、`16:9`、`9:16`、`2:3`、`3:2` 和 `21:9`；主体容器本身不随比例变高或变宽。
- 最终生成图片继续使用原有展示尺寸，不跟随占位卡片缩小。
- 只对中央小画布使用轻微呼吸动画；当系统启用“减少动态效果”时停用动画。
- 只有“生成中、耗时较长、失败、取消”等阶段变化文案使用 `aria-live="polite"`。每秒变化的可见等待时间不放进 live region，避免辅助阅读工具反复播报。

不显示百分比或预计剩余时间，因为当前 provider 没有提供真实进度。

## 多图布局

带有 `metadata.source === "image_generation"` 的连续附件使用生成图片拼图；普通用户附件和其他 Tool 附件继续使用现有附件布局。

- 1 张：显示一张较大的预览图。
- 2 张：两列并排。
- 3 张：左侧一张大图，右侧上下两张小图。
- 4 张：2×2。
- 5 张及以上：默认显示前 4 张，第四格覆盖 `+N`；点击后在当前消息中展开全部图片，并可再次收起。
- 窄窗口退化为两列，不出现横向滚动。

拼图缩略图允许使用 `object-fit: cover` 保持整齐，但不会修改附件原图。每张图片继续复用现有 `MessageAttachment` 的预览、打开和另存为能力。

## 消息顺序

生图专用单元保留 Tool 部件原本的位置。助手消息中的内容顺序不变：

```text
生图前的说明文字
→ 生成占位符，成功后由生成图片组接替
→ 生图后的总结文字
```

同一条助手消息中出现多次 `ImageGeneration` 时，每个 Tool 使用自己的稳定 ID 和状态，互不影响。

## 简化范围

本次明确不做：

- 不新增服务端进度事件。
- 不新增数据库表或消息部件类型。
- 不修改 `metadata.generatedImages` 数据结构。
- 不实现多图部分成功；继续使用当前整批成功或整批失败的行为。
- 不实现单张图片重试。
- 不实现新的灯箱或图库页面。
- 不改变附件存储、引用统计、打开或另存为流程。
- 不在生成开始前猜测图片数量。当前 Tool 没有数量参数，只有 provider 返回后才能按附件数量选择单图或多图布局。

## 测试

桌面端测试覆盖：

1. `pending` 和 `running` 的 `ImageGeneration` 显示占位符，并且不进入普通 Tool 活动分组。
2. `ratio` 映射为安全的占位区域比例，无效值回退到 `1:1`。
3. 等待时间跨过 10 秒和 45 秒时使用对应文案。
4. `completed` 后显示现有生成附件，不重复显示 Tool 活动行。
5. `failed`、`interrupted` 和完成但缺少附件时显示明确状态。
6. 1、2、3、4 和 5 张以上图片使用对应布局，展开和收起有效。
7. 普通消息附件继续使用现有布局。
8. 一条消息中多次调用 `ImageGeneration` 时，状态和附件顺序正确。
9. 现有图片预览、打开、另存为以及完整桌面测试不退化。
