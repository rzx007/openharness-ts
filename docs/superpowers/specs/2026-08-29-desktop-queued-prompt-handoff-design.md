# 桌面端排队消息自动接管展示设计

## 问题

运行中追加的普通消息先进入待处理队列。上一轮结束后，下一条 pending run 会被桌面端视为即将启动的主 run，并从待处理区隐藏；但服务端要到 `run.started` 才投影真实用户消息。这个交接窗口只显示“正在处理”，看不到正在执行的提问。

## 目标

- 不改变 queue、steer 和自动调度语义。
- 排队消息被选为下一轮后，立即在正文显示为用户消息。
- 服务端真实用户消息到达后无缝接管，不重复、不闪回。
- 仍保留首条普通消息不闪入待处理队列的现有行为。

## 方案

由对话页识别“当前没有 running run，但存在最早 pending run”的自动接管窗口。若该 pending run 对应的真实用户消息尚未进入正文，则把同一 input 作为乐观用户消息合并到正文；待处理队列继续隐藏这个即将启动的 run。

乐观消息使用服务端 input 的 ID、内容和附件构建，不创建假的 cursor 或 run。真实消息出现后，合并逻辑按 input ID 去重并停止生成乐观消息。

正在提升或取消的队列项不参与自动接管，避免旧 SSE 快照让已经操作的消息短暂进入正文；操作失败后，该消息可以重新参与正常交接。

首条普通消息继续使用现有本地 `placement: transcript` 乐观记录；本次只补齐已由服务端确认、但用户消息尚未投影的 pending run。

## 数据流

1. 运行中追加消息，待处理区显示该消息。
2. 上一轮完成，下一条 run 保持 pending，且没有其他 running run。
3. 待处理区隐藏这条即将启动的 run；正文同时生成对应的乐观用户消息。
4. 页面在该用户消息下显示“正在处理”。
5. `run.started` 投影真实用户消息；按 input ID 去掉乐观消息，真实消息接管。

## 测试

- 单个 pending follow-up、没有 running run、正文尚无对应消息时，正文立即显示该用户输入。
- 正文已有对应真实用户消息时，不生成重复乐观消息。
- 有 running run 时，后续 pending 消息仍只显示在待处理队列，不提前进入正文。
- 现有“首条普通消息不闪入待处理队列”和队列操作测试继续通过。
