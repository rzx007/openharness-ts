# 对话附件小型发布收口设计

日期：2026-08-29  
状态：待用户书面确认  
分支：`codex/attachment-release-closeout`

## 1. 目标

在桌面端设置页增加一个小而完整的“存储”页面，把已经具备的附件存储诊断能力暴露给用户。用户能够看懂附件占用了多少空间、存储是否正常，并主动执行安全修复或清理。

这一阶段不改变上传、发送、模型输入、OCR 降级或附件保存流程。它只负责发布前的可见性、维护入口和必要反馈。

## 2. 范围

本阶段包含：

- 设置侧栏增加“存储”入口；
- 页面打开后自动扫描一次附件存储；
- 展示附件数量、唯一文件数量、实际占用、逻辑大小、去重节省、活跃占用和可清理空间；
- 展示存储问题，并把底层问题代码翻译成用户能看懂的说明；
- 支持手动重新扫描；
- 支持安全修复过期占用标记和孤立文件；
- 支持在二次确认后清理符合回收规则的数据；
- 展示操作中的状态、操作结果和失败信息；
- 补齐页面单元测试、IPC 使用测试和必要文档。

本阶段不包含：

- 自动清理开关；
- 存储配额和告警阈值；
- 逐文件浏览、预览或删除；
- 日志、数据库、缓存等通用诊断中心；
- 新增后台定时任务；
- 修改现有附件存储策略；
- 兼容旧附件数据。

## 3. 页面位置与信息结构

侧栏“编码”分组新增：

```text
编码
├── 终端
├── Git
├── 运行环境
└── 存储
```

选择“存储”后，主内容标题为“附件存储”。它强调这是本地工作区附件数据，避免用户误认为这是云端账号空间。

页面从上到下只有三块：

1. 空间概览；
2. 健康检查；
3. 维护操作。

不再增加二级导航或高级设置。

## 4. 视觉约束

实现必须保持项目已经确定的设置页风格，视觉原型只表达信息层级，不是新的设计系统。

- 页面继续使用 `bg-conversation`、现有前景色和 muted 色，不写独立主题色；
- 标题继续使用 `font-heading` 和设置页现有字号；
- 内容宽度、左右留白和纵向间距沿用 `SettingsContent`；
- 卡片使用项目现有边框、背景、圆角和阴影 token；
- 按钮、提示、确认弹窗、骨架屏使用已有 UI 组件；
- 图标统一使用 Lucide，不使用 Emoji 或字符图标；
- 正常状态使用低饱和的正向色，警告和错误只出现在确实需要用户关注的位置；
- 不做后台仪表盘式的大号数字墙，不使用渐变、玻璃拟态或新的装饰语言；
- 支持现有明暗主题和键盘焦点样式。

## 5. 数据来源

页面只调用已经存在的 Desktop API：

```ts
window.desktop.attachments.scanStorage()
window.desktop.attachments.repairStorage()
window.desktop.attachments.gcStorage()
```

主进程继续通过现有 IPC 和 Client 调用 daemon。渲染层不直接访问数据库或附件目录，也不新增另一套统计逻辑。

`scanStorage()` 返回的数据分为：

- `summary`：数量和字节统计；
- `issues`：缺失文件、大小不一致、孤立文件、过期占用、已删除附件残留；
- `latestGcAudit`：最近一次清理审计。

修复和清理成功后，页面再次调用 `scanStorage()`，最终显示服务端重新计算的结果，不在前端自行猜测新数值。

## 6. 页面状态

页面用一个局部状态容器管理：

```text
首次进入
  -> 扫描中
  -> 扫描成功 -> 展示概览和问题
  -> 扫描失败 -> 展示错误和“重试”

展示状态
  -> 手动扫描 -> 保留旧数据并显示刷新状态
  -> 安全修复 -> 禁用维护按钮 -> 修复成功 -> 重新扫描
  -> 清理确认 -> 用户取消 / 用户确认
  -> 清理执行 -> 禁用维护按钮 -> 清理成功 -> 重新扫描
```

首次扫描时显示与最终布局接近的骨架屏，避免页面跳动。已有结果后的刷新不清空页面，只在按钮和扫描时间位置显示正在刷新。

同一时间只允许一个维护操作。扫描、修复和清理都必须能防止重复点击。

## 7. 空间概览

空间概览显示：

- 实际占用：`physicalBytes`；
- 附件总数：四种资产状态数量之和；
- 可用附件：`assets.ready`；
- 唯一文件：`uniqueBlobs`；
- 去重节省：`deduplicatedBytes`；
- 可清理空间：`reclaimableBytes`；
- 正在使用：`activeLeases`；
- 处理失败：`assets.failed`。

字节统一用一个纯函数格式化为 `B`、`KB`、`MB`、`GB`、`TB`，最多保留一位小数。零值显示 `0 B`，非法或负数按 `0 B` 处理，避免界面出现 `NaN`。

去重节省和可清理空间是补充信息，不把它们和实际占用相加成一个误导性的总量。没有磁盘容量上限数据，因此不展示“已使用百分比”。

## 8. 健康检查

底层问题代码映射为固定用户文案：

| 问题代码 | 用户说明 | 可执行动作 |
| --- | --- | --- |
| `missing_blob` | 附件记录存在，但本地文件缺失 | 提示重新扫描后仍存在则保留错误，不承诺自动恢复 |
| `size_mismatch` | 附件文件大小与记录不一致 | 提示数据异常，不由安全修复删除 |
| `orphan_blob` | 本地存在没有附件记录引用的文件 | 可安全修复 |
| `stale_lease` | 发现已经过期的占用标记 | 可安全修复 |
| `deleted_asset_retained` | 已删除附件仍在保留期或等待回收 | 可进入垃圾清理，但仍由服务端规则决定是否删除 |

页面按代码聚合问题数量，不默认暴露 `assetId`、哈希或文件系统路径。这样既避免信息噪声，也避免把内部标识当作用户可操作对象。

当没有问题时显示简短正常状态。当存在错误级问题时，页面状态改为“需要检查”；只有可安全处理的问题时显示“可修复”。

## 9. 安全修复

“安全修复”直接调用 `repairStorage()`，但按钮旁必须说明它实际做什么：清除过期占用标记，并删除没有任何附件记录引用的孤立文件。

安全修复不弹确认框，因为接口语义已经限制在可确定安全的项目。完成后显示：

- 清除的过期占用数量；
- 删除的孤立文件数量；
- 释放空间。

如果没有可修复问题，按钮禁用并显示“无需修复”。

## 10. 垃圾清理

“清理无用附件”会删除数据，因此必须先打开确认弹窗。弹窗明确说明：

- 只处理已经标记删除且满足保留期的数据；
- 有对话引用、活跃占用或共享文件的数据会跳过；
- 删除后不能从本地附件存储恢复；
- 当前扫描估算可清理空间只作提示，实际结果由执行时状态决定。

用户确认后调用 `gcStorage()`。完成反馈显示扫描数量、删除附件数量、删除文件数量、释放空间，以及错误数量。存在单项删除失败时，操作不伪装成全部成功，页面显示“部分完成”并允许重新扫描或重试。

当 `reclaimableBytes` 为零且没有 `deleted_asset_retained` 问题时，清理按钮禁用并显示“暂无可清理内容”。

## 11. 错误与反馈

- 扫描失败：页面保留明确错误区和重试按钮；
- 刷新失败：保留旧结果并提示结果可能已过期；
- 修复失败：不修改当前统计，展示失败提示；
- 清理失败：重新扫描以获取真实状态；若重新扫描也失败，则保留操作错误；
- Desktop API 不可用：显示“当前环境不支持附件存储诊断”，不让页面崩溃；
- 所有错误使用用户能理解的固定前缀，具体底层错误只作为补充内容。

反馈放在当前页面内，不依赖暂时性 toast 承载唯一结果。辅助 toast 可以有，但不是本阶段的必需项。

## 13. 测试与验收

至少覆盖：

1. “存储”导航标签与 `storage` slug 双向映射；
2. 字节格式化边界；
3. 四种资产状态汇总；
4. 问题按代码聚合；
5. 首次加载调用扫描；
6. 扫描成功展示核心统计；
7. 扫描失败可以重试；
8. 安全修复完成后重新扫描；
9. 清理必须经过确认；
10. 用户取消确认时不调用清理；
11. 清理完成后展示结果并重新扫描；
12. 操作中防止重复执行；
13. Desktop API 缺失时有明确降级界面。

视觉验收包括：

- 与现有设置页并排查看时没有风格断层；
- 浅色和深色主题都可读；
- 窄窗口不出现横向溢出；
- 键盘能访问扫描、修复、清理和确认弹窗；
- 状态信息不只靠颜色表达；
- 数字较大、问题较多和错误文案较长时布局仍稳定。

完成后运行相关单测、桌面端类型检查和仓库级测试；最后在桌面应用中实际打开页面，至少完成扫描、取消清理确认和错误状态的视觉检查。

## 14. 完成标准

满足以下条件才算小型发布收口完成：

- 用户可以从设置页找到附件存储状态；
- 页面所有数字都来自现有诊断接口；
- 修复和清理的影响范围写得清楚；
- 删除性清理必须二次确认；
- 操作后的页面数据来自重新扫描；
- 接口异常不会导致设置页崩溃；
- 页面严格沿用现有设计系统；
- 自动化测试和人工视觉检查通过；
- 不把本阶段扩成附件文件管理器或通用诊断中心。
